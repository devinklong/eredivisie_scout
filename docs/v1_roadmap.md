# v1 Roadmap

What's still unbuilt for v1 (no xG — see README's v2 note for that scope). This is a build plan, not a bug list — see `patch_list.md` for actual fixes to existing code.

## Extraction / derivation

1. **Passing derivation function — DONE.** `passes_completed`/`passes`/`passes_pct` computed from WhoScored raw events (`.isin()` on `Pass`/`BlockedPass`/`OffsidePass`, not a direct `==` match — confirmed via qualifier overlap testing that this correctly captures crosses/through-balls/throw-ins nested inside `qualifiers`, not as separate `type` values).

2. **Possession derivation function — DONE.** Touches by zone, take-ons, from raw events. `carries` remains out of scope for v1 (needs SPADL output format, `output_fmt="spadl"`, not the default event format — never built, deliberately deferred).

3. **Defense derivation function — DONE.** Tackles/interceptions/clearances by zone from raw events. `Challenge`/`dribbled_past` corrected from an initial false win/loss split — confirmed via Opta's own event definitions that `Challenge` is a losing-side-only event, with no corresponding "win" outcome on that same event type.

4. **Final-third/penalty-area entry proxy — DONE.** Zone-geometry check on `end_x`/`end_y` from completed `Pass` events. Serves as the SCA/GCA substitute for v1 (true SCA chain-attribution deferred, not planned for v1 at all). Carries-based entries out of scope, same as item 2.

5. **WhoScored season-scale batch extraction — DONE and verified for 2013-14 through 2025-26. Historical coverage fully mapped for all of 2010-11 through 2025-26 (2026-09-02).** `pipelines/whoscored/scrape_all_whoscored_matches.py` ran all four derivation functions above against every match in each season, dumping per-match JSON to `data/whoscored/{season}/`. Enabled by the `force_cache=True` fix (see `patch_list.md`) — without it this would have taken 10-20+ hours/season; with it, real runs completed at ~20s/match.
   - **2020-21 through 2025-26: clean.** 2025-26/2024-25 each had 3 missing (playoff matches, see below); 2022-23 had 6 (3 separate two-legged playoff ties, confirmed via consecutive-pair ID pattern); 2020-21 and 2021-22 had 0 missing. All verified via `tests/whoscored/verify_whoscored_batch.py`, structurally valid, no malformed data. 2025-26 additionally hand spot-checked (most/least-active matches) against the goalkeeper-touch-distribution sanity pattern that caught a real bug earlier — held up correctly.
   - **Playoff matches (2-6 per season depending on how many promotion/relegation ties occurred that year) are consistently excluded** — confirmed via WhoScored's own separate "Eredivisie ECL Playoff" stage categorization, and via the fixed regular-season count (always exactly 306) holding steady while only the variable playoff count changed. Out of scope for this project's regular-season thesis anyway.
   - **2019-20: deliberately lighter, NOT a bug.** 197/250 matches succeeded. The season was suspended 12 March 2020 and formally annulled by the KNVB 24 April 2020 due to COVID-19, after each club had played ~25 of 34 scheduled matches — no champion, no promotion/relegation that year. The 53 "missing" matches never happened in real life; confirmed via external search.
   - **2013-14 through 2018-19: fallback parser integrated and CONFIRMED across all 6 seasons (2026-09-01/02).** `parse_raw_whoscored_events.py` wired into `scrape_all_whoscored_matches.py` via `get_events_with_fallback()` -- tries the standard path first, catches specifically the confirmed casting `TypeError` (not a blanket catch-all), falls back to the raw-JSON parser only then. **All 6 seasons clean: 2013-14, 2014-15, 2015-16, 2016-17, 2017-18 each 0 missing; 2018-19 312/313 (1 genuine single-match gap, not systemic).**
   - **2010-11 through 2012-13: CONFIRMED genuine data gaps on WhoScored's own side, not a bug.** 2010-11 and 2011-12 failed on every single match with no data found at all. 2012-13: 311/312 missing -- essentially the entire season. This is a hard cutoff, not a gradual fade -- 2012-13 and 2013-14 sit right on either side of a sharp boundary. Not fixable via the fallback parser (which only helps when real data exists but soccerdata's formatting crashes) -- WhoScored genuinely has nothing here. A stale `data/whoscored/2012-13/` folder exists from early testing (pre-fix format) — inert, out of scope, flagged for cleanup in `patch_list.md`.
   - **FINAL CONFIRMED RANGE: 2013-14 through 2025-26 (13 full seasons) is real, usable WhoScored data.** This directly answers the original "what's the realistic model start date" question with actual evidence, not inference -- 2013-14, not 2015, is the true boundary. 2019-20 remains a genuine partial season (COVID) within this range, not a gap.

6. **WhoScored data — loaded into Postgres for all 13 confirmed seasons (2013-14 through 2025-26), team-attribution bug fixed, whoscored_player_id backfilled. FULLY CLOSED (2026-09-04).** Real gap caught by user: the original `derive_*.py` functions grouped only by player name, silently dropping which club each player played for -- made it impossible to answer a basic query like "show Ajax's 2025-26 squad." Fixed across all four `derive_*.py` files (`.groupby(["player", "team"])` instead of `.groupby("player")`), which required switching `scrape_all_whoscored_matches.py`'s JSON output from `orient="index"` (dict keyed by player name, incompatible with a team field) to `orient="records"` (list of dicts, each with explicit `player`/`team` keys) -- a JSON object key can't hold a (player, team) tuple. All 13 seasons' per-match JSON regenerated from soccerdata's already-cached raw events (fast -- no re-scraping needed). `schema/whoscored/eredivisie_whoscored_player_season_stats.sql` created, keyed `(player_name, team, season_id)`. `pipelines/whoscored/aggregate_and_load_whoscored_season.py` aggregates additive counting stats across a player's matches within each season/team (percentages recomputed from summed totals, never averaged across matches), loops all 13 seasons, loaded and confirmed -- Ajax's squad correctly queryable per season.
   - **`whoscored_player_id` backfill, fully closed and verified (2026-09-04).** WhoScored's native `player_id` (present in raw events all along, just not preserved by the derive functions) is now carried through into a dedicated `whoscored_player_id` column -- a within-source identity signal, separate from Transfermarkt's `player_id` namespace, useful as an entity-resolution cross-check later. Full debugging trail (stale JSON, `ON CONFLICT DO NOTHING` vs `DO UPDATE`, `execute_values` rowcount paging, a `sd.WhoScored()`-launches-Chrome-despite-caching issue worked around via a local cache-only reprocessing script, and 3 orphaned garbage rows from an older load) is in `patch_list.md`. Table re-verified clean: zero rows with `whoscored_player_id IS NULL`, zero rows with a non-name `player_name`.

7. **Transfermarkt scraper — full pipeline complete, in Postgres (2026-08-29/30).** All 29 clubs scraped, filtered against `eredivisie_club_status`, and loaded into `eredivisie_transfers` via `pipelines/transfermarkt/load_eredivisie_transfers.py` — confirmed 8,060 rows inserted, matches `SELECT COUNT(*)` exactly. 8. **Loan buy-option/obligation-to-buy data point — not captured, needs its own source. Reconfirmed out of scope for now (2026-08-30).** Confirmed real gap: whether a loan carries a buy-option or obligation-to-buy clause isn't encoded anywhere in the scraped transfer-history data (e.g. Arokodare's loan to Wolves shows plain "loan transfer" despite genuinely including an option to buy). `fee_type` already distinguishes permanent vs. loan vs. paid/unpaid loan — that part is done. The specific option/obligation distinction is a different, unbuilt data source: likely each player's individual transfer-detail page (not the club-level page already scraped), probably reported in prose rather than a structured field, and possibly undisclosed for many transfers regardless. Re-raised and re-declined tonight rather than investigated further, to avoid opening new unconfirmed-structure scraping work this late in a session. Do not infer "no option/obligation" from a loan's current fee_type — this dimension simply isn't in the data at all, not false.

9. **soccerdata (FBref) player-season stats — loaded into Postgres, both known-bad rows fixed and verified (2026-08-30). CLOSED.** `pipelines/soccerdata/load_eredivisie_player_stats.py` loaded all 16 seasons into `eredivisie_player_season_stats`/`eredivisie_keeper_season_stats`. Two intermediate conclusions in this file were wrong and got corrected in sequence -- keeping the trail since it's a real example of verifying rather than assuming:
   - First assumed: exact duplicate source rows, harmless. Wrong -- the two rows per player had different stat values.
   - Second assumed (from the differing values alone): two different real people sharing a name. Wrong -- assumed too fast from internal data disagreement without checking real-world facts.
   - **Verified via external search (Wikipedia, worldfootball.net, FBref's own current player pages, Soccerway): both are ONE real person each, with FBref's own data containing a genuine erroneous duplicate row.** Ricardo Ippel (real DOB 31 Aug 1990, Willem II 2010-2015) -- one row had a wrong born/age (1991/22). Bilal Bayazit (real DOB 8 Apr 1999, Dutch GK, Vitesse 2017-2021) -- one row wrongly listed him as an Icelandic defender. Not a name-collision risk for entity resolution generally -- an isolated FBref data-quality glitch on these 2 specific rows.
   - **Fixed (2026-08-30) via `tests/soccerdata/fix_duplicate_player_rows.py`**: additive counting stats (matches played, minutes, starts, sub appearances) summed across both source rows per player; identity fields (nation/position/born) set to the externally-verified real values; rate stats recomputed from the merged totals. Both `UPDATE`s confirmed 1 row affected each. Final numbers make sense: Ippel 8 MP/151 min/8 sub appearances/18 unused subs (real rotation-player profile); Bayazit 0 MP/0 min/7 unused subs (matches his real career as Vitesse's backup keeper that era). Table count correctly remains 9,229 (a content fix to 2 existing rows, not 2 additions). `(player_name, team, season_id)` kept as the unique key, unchanged. Confirmed already had team captured correctly from the start (soccerdata's own multi-index is `(league, season, team, player)` natively) — no equivalent team-attribution bug here, unlike WhoScored's item 6.

10. **Entity resolution across sources — extraction and data-quality work now FULLY closed on all three sources (2026-09-04). This is the current, active next phase.** FBref/soccerdata and WhoScored both have NO numeric player ID usable across sources (WhoScored's `whoscored_player_id`, added 2026-09-04, is a within-source identity signal only — see item 6 — not a cross-source key); Transfermarkt's `spieler/{id}` is a confirmed clean join key. Cross-source matching will need fuzzy name matching, not a clean ID join, for the FBref↔WhoScored↔Transfermarkt links.

    **Confirmed row-identity / join keys per table (as of 2026-09-04):**

    | Table | Row identity (unique key) | How it links across sources |
    |---|---|---|
    | `eredivisie_transfers` (Transfermarkt) | `transfer_id` (surrogate PK) | `player_id` (Transfermarkt's own numeric ID) is the clean, confirmed cross-table key on this side. `own_club_id`/`counterparty_club_id` + `season_id` join to `eredivisie_club_status`. |
    | `eredivisie_club_status` (Transfermarkt) | `club_id` + `season_id` | Reference/lookup table — not itself a fuzzy-matching target. |
    | `eredivisie_player_season_stats` (soccerdata/FBref) | `player_name` + `team` + `season_id` | No numeric ID — fuzzy-match target. |
    | `eredivisie_keeper_season_stats` (soccerdata/FBref) | `player_name` + `team` + `season_id` | No numeric ID — fuzzy-match target. |
    | `eredivisie_whoscored_player_season_stats` (WhoScored) | `player_name` + `team` + `season_id` | No cross-source numeric ID. `whoscored_player_id` (native, WhoScored-only) usable as an additional within-source consistency check, confirmed clean 2026-09-04 — not a join key to the other two sources. |

    **Planned approach (decided in a separate entity-resolution planning session, 2026-09-04):**
    - A new synthetic, source-independent canonical `player_id` (not Transfermarkt's `spieler/{id}`) plus a separate crosswalk/junction table: `(player_id, source, source_key, confidence, match_method, verified)` — not one column per source on a wide `players` table.
    - Match FBref↔WhoScored to each other first (closer naming conventions, no Transfermarkt intermediary needed), then join that merged pair to Transfermarkt's `player_id` as a second pass.
    - Block on `name + team + season_id` before fuzzy-scoring (not name alone — the Ippel/Bayazit collision already proved name-only matching is unsafe even within one source). Incorporate birth year as an additional disambiguating signal where available on both sides of a candidate pair.
    - Matching metric: Jaro-Winkler (rewards shared name prefixes) plus a token-sort comparison (handles word-order differences), taking the lower of the two scores as the working confidence — not yet reduced to a single objective formula, deliberately deferred until real candidate-pair examples are in hand.
    - Same-name/same-season/different-club cases: cross-reference `eredivisie_transfers` for a matching transfer record before deciding one-player-transferred vs. two-different-people; default to manual review, not auto-linking, when ambiguous.
    - Mid-season transfers: kept as two separate season-stat rows per player (one per club-stint), linked to the same canonical `player_id` in the crosswalk — a deliberate design decision, not a limitation.
    - A new `cleaning_logs/` folder (mirroring the existing per-source `pipelines/`/`tests/` split) will hold fuzzy-match candidate pairs and the manual-review queue.
    - Validation: systematize the Ippel/Bayazit external-verification discipline — stratified sample across confidence bands, externally checked (Wikipedia/worldfootball.net/Transfermarkt bios), to empirically calibrate the auto-link threshold rather than guessing one.

## Reference findings (not action items, just context worth keeping)

- Confirmed FBref's Opta-sourced advanced stats (passing/passing_types/goal_shot_creation/defense/possession/keeper_adv) are unavailable — retroactively, across all tested seasons (current, 2025-26, 2021-22) — due to a January 2026 provider license termination. Not a scraper bug, not fixable.
- Checked and ruled out FootyStats and FotMob as scrape targets — both have explicit anti-scraping clauses in their Terms of Service.
- Checked and ruled out worldfootballR's FotMob support (dropped years ago per its own changelog) and the package itself (now unmaintained) as a data source.
- **`counterparty_club_name: "Unknown"` does NOT reliably mean a defunct/folded club.** Confirmed via a real example: Marquinho's 2004 departure from PSV shows `"Unknown"`, but the actual destination (Alianza Lima, Peru) is a real, currently-existing club — Transfermarkt simply has no linked club reference for that specific transfer. Treat `"Unknown"` as "Transfermarkt has a data gap here," not as a signal about the club's real-world status. Identifying the true counterparty for any of these rows requires independent research per row, not something inferable from the scraped data itself.
- **WhoScored's team-name field may not match Transfermarkt/soccerdata's convention exactly** — spot-checked during the `whoscored_player_id` debugging: a WhoScored row showed `"PSV Eindhoven"` where `eredivisie_club_status` and other tables consistently use `"PSV"`. Not yet systematically checked across all clubs/sources, but worth resolving before entity resolution's `team` blocking key is trusted at scale — a straight string match would silently fail for any club where the two sources disagree on naming.
