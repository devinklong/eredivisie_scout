# Patch List

Fixes to things that were built, ran, and behaved wrong — not a build plan. See `v1_roadmap.md` for what's still unbuilt.

## Open

1. **WhoScored `read_events()` reliability** — has crashed on 3 separate runs now (2026-08-27 morning, 2026-08-27 afternoon, 2026-08-28), always the same `_is_captcha_present()` TypeError on `None` page_source, always self-heals on retry within the same script run. **Likely real cause, per user (2026-08-28): closing/minimizing the automated Chrome tab mid-run.** SeleniumBase's UC mode pops up a real visible browser window during each `read_events()` call — if that tab gets closed or loses focus while the script is still working, the driver loses its window handle, which matches the `window_handles[-1]` IndexError seen once and is consistent with the browser-session-death pattern behind the other two crashes. Not a soccerdata bug — a workflow habit to fix: leave the SeleniumBase-launched Chrome window alone (don't close/minimize it) until the script finishes. Never recurred after this habit was adopted — no longer chased further, but left open in case it resurfaces during future WhoScored work (e.g. re-running for a new season).

2. **WhoScored team-attribution bug — see Done below for the fix; flagged here as a pattern to watch for.** The original `derive_*.py` functions grouped only by player name, silently dropping team, for weeks before being caught. Worth remembering this class of bug (a groupby silently losing a real dimension) could recur if new derive functions get added later — no specific open instance right now, just a reminder.

3. **`sd.WhoScored()` launches a live Chrome window even when every request should be cache-covered — root cause not conclusively isolated (2026-09-04).** Reprocessing all 13 seasons' already-cached matches through the original `scrape_all_whoscored_matches.py` (to regenerate JSON with the newly player_id-inclusive derive functions) unexpectedly popped up live SeleniumBase Chrome windows, despite `force_cache=True` and despite every match having succeeded in the original extraction. Two candidate explanations, neither confirmed: (a) `sd.WhoScored()`'s constructor itself may launch a browser session on instantiation regardless of whether any individual request needs one, or (b) `output_fmt="raw"` (used by the six pre-2019 fallback-parser seasons) may cache under a separate namespace from the default format, meaning only matches that originally hit the casting bug had their raw-format response cached — every other match in those seasons would have no raw-format cache entry at all. Not chased to a definitive root cause since a workaround was sufficient (see Done below) — worth revisiting if this resurfaces in a context where the workaround doesn't apply.

4. **`data/whoscored/2012-13/` is stale leftover clutter, not part of the real pipeline — confirmed 2026-09-04, worth deleting.** Contains at least one file (`611804.json`) in a format that doesn't match the current pipeline's output shape at all (a plain list of player-name strings per category, not a list of `{player, team, ...stats}` dicts) — almost certainly a leftover from early pre-fix testing. 2012-13 was already confirmed out of scope entirely (a genuine WhoScored data gap, not one of the 13 real usable seasons — see `v1_roadmap.md`), so this folder is never touched by either production script. It's inert, but a directory-wide scan (rather than one scoped to the 13 real `SEASONS`) will pick it up and produce false leads, as it did during the `whoscored_player_id` debugging below. Not deleted yet — flagged for cleanup.

  - **Inspect first, as with the transfer pages.** `inspect_league_season.py` on Serie A 2019, Premier League 2012 and Ligue 1 2023 showed: the URL shape `/{slug}/startseite/wettbewerb/{code}?saison_id={year}` works and the season parameter is honored (titles read `Serie A 19/20`); the participants table is the `class='items'` table under a heading like `Clubs - Serie A 19/20`; several other tables (standings, fixtures) hold the same clubs; and small tables hold NON-members (Ligue 1 2023's `Subsequent competitions` had three, ids 10004, 618 and 11273), so counting every club link on the page is wrong. - **Modeling phase, step 1: position-relative style percentiles (`player_season_style_percentiles`) — built, run on real data, one source bug found and fixed (2026-10-06).** `pipelines/modeling/build_style_percentiles.py`, 33 offline tests, 22 mutations caught (the runner now refuses to run against a failing baseline: one earlier mutation pass ran against a baseline broken by a wrong expectation in a test I had just added, which made every mutation look caught, and was redone), plus an end-to-end run in a real Postgres on `Decimal`-typed data including a re-run and a failed write that leaves the previous table intact. A raw stat mostly measures role (the audit's `ws_touches_def_pen_area` flagged 31 of 31 outliers as keepers), so each outfield player-season is ranked by mean percentile rank, (L + 0.5E)/N, within (season, primary position), where primary position is the first token of `fbref_position`.
  - **Design decisions, each made on data:** (1) a sale in transfer-season s uses stats from season s-1, the last completed season, since a sold player's season-s stats are partial or at a new club and include post-decision performance (the same leakage class as the spend shares). (2) Goalkeepers are out of v1 (about 25 a season is too few to rank, and `gk_*` against outfield stats splits them trivially). (3) Same-season percentiles; every DF/MF/FW group has 75 or more ranked players a season. (4) Train from sale season 2014 onward: WhoScored starts in 2013 and a sale needs stats from the season before it. (5) Style features (about 30, per-90 or rate) feed clustering; outcome stats (goals, assists, efficiency) go to the valuation model only; team-context stats, cards and errors are not features; `ws_ground_duel_win_pct` is out of v1 because it has no attempt count to guard it.
  - **The id spaces differ, and a direct join would have been wrong:** `eredivisie_transfers.player_id` is a Transfermarkt id and `master_player_season_stats.player_id` is canonical. A direct join matched 0 of 709 sales; it must go through `player_source_crosswalk` (`source = 'transfermarkt'`, `source_native_id`), de-duplicated because a canonical player can carry several crosswalk rows for one Transfermarkt id (the PSV-style fan-out). Zero Transfermarkt ids map to more than one canonical player. A direct join between unrelated id spaces can also match the WRONG player when two numbers coincide, which here happened not to occur.

- **Audit blind spot: a column of zeros passes a NULL audit. Scan built and run (2026-10-06).** The audit's coverage checks count NULLs, and a column of zeros is 100% populated. FBref returns literal zeros, not NULL, for data it does not have: shots in 2016-2017 (patch list, 2026-09-14) and, found by the percentile script's constant guard, crosses, offsides and fouls drawn in the same seasons. The audit recorded those misc columns as having "real values in 2017" because they were not NULL. This is the same shape as the empty keeper table found earlier (zero findings is not the same as healthy), and it means any `fbref_*` or `gk_*` column could be zeros in 2016-2017 without the audit having said so, including `fbref_interceptions`, `fbref_tackles_won` and the keeper stats the project plans to reconstruct. `data_audit/find_constant_columns.py` closes it: per numeric column of `master_player_season_stats`, per season, among rows with 5+ nineties, it reports `constant` (every value identical, usually 0), `empty` (all NULL) and `sparse` (fewer than 30 values), judging `gk_*` columns on keeper rows only and everything else on outfield rows only, and writes `data_audit/results/constant_columns.csv`. 17 offline tests, 13 mutations caught against verified-clean baselines, and an end-to-end run in a real Postgres on `Decimal` and text columns. It names suspects, it does not convict: a legitimately rare event can be all-zero in a small season. **Result on the real data:** 134 numeric columns judged, 464 (column, season) findings, and NO `sparse` findings, which closes the open question: the 2010-2015 emptiness of crosses, fouls drawn and interceptions is true emptiness, not the 30-value minimum hiding partial data.
