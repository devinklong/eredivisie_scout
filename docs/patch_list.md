# Patch List

Fixes to things that were built, ran, and behaved wrong — not a build plan. See `v1_roadmap.md` for what's still unbuilt.

## Open

1. **WhoScored `read_events()` reliability** — has crashed on 3 separate runs now (2026-08-27 morning, 2026-08-27 afternoon, 2026-08-28), always the same `_is_captcha_present()` TypeError on `None` page_source, always self-heals on retry within the same script run. **Likely real cause, per user (2026-08-28): closing/minimizing the automated Chrome tab mid-run.** SeleniumBase's UC mode pops up a real visible browser window during each `read_events()` call — if that tab gets closed or loses focus while the script is still working, the driver loses its window handle, which matches the `window_handles[-1]` IndexError seen once and is consistent with the browser-session-death pattern behind the other two crashes. Not a soccerdata bug — a workflow habit to fix: leave the SeleniumBase-launched Chrome window alone (don't close/minimize it) until the script finishes. Never recurred after this habit was adopted — no longer chased further, but left open in case it resurfaces during future WhoScored work (e.g. re-running for a new season).

2. **WhoScored team-attribution bug — see Done below for the fix; flagged here as a pattern to watch for.** The original `derive_*.py` functions grouped only by player name, silently dropping team, for weeks before being caught. Worth remembering this class of bug (a groupby silently losing a real dimension) could recur if new derive functions get added later — no specific open instance right now, just a reminder.

3. **`sd.WhoScored()` launches a live Chrome window even when every request should be cache-covered — root cause not conclusively isolated (2026-09-04).** Reprocessing all 13 seasons' already-cached matches through the original `scrape_all_whoscored_matches.py` (to regenerate JSON with the newly player_id-inclusive derive functions) unexpectedly popped up live SeleniumBase Chrome windows, despite `force_cache=True` and despite every match having succeeded in the original extraction. Two candidate explanations, neither confirmed: (a) `sd.WhoScored()`'s constructor itself may launch a browser session on instantiation regardless of whether any individual request needs one, or (b) `output_fmt="raw"` (used by the six pre-2019 fallback-parser seasons) may cache under a separate namespace from the default format, meaning only matches that originally hit the casting bug had their raw-format response cached — every other match in those seasons would have no raw-format cache entry at all. Not chased to a definitive root cause since a workaround was sufficient (see Done below) — worth revisiting if this resurfaces in a context where the workaround doesn't apply.

4. **`data/whoscored/2012-13/` is stale leftover clutter, not part of the real pipeline — confirmed 2026-09-04, worth deleting.** Contains at least one file (`611804.json`) in a format that doesn't match the current pipeline's output shape at all (a plain list of player-name strings per category, not a list of `{player, team, ...stats}` dicts) — almost certainly a leftover from early pre-fix testing. 2012-13 was already confirmed out of scope entirely (a genuine WhoScored data gap, not one of the 13 real usable seasons — see `v1_roadmap.md`), so this folder is never touched by either production script. It's inert, but a directory-wide scan (rather than one scoped to the 13 real `SEASONS`) will pick it up and produce false leads, as it did during the `whoscored_player_id` debugging below. Not deleted yet — flagged for cleanup.
