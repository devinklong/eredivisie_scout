# Patch List

Fixes to things that were built, ran, and behaved wrong — not a build plan. See `v1_roadmap.md` for what's still unbuilt.

## Open

1. **WhoScored `read_events()` reliability** — has crashed on 3 separate runs now (2026-08-27 morning, 2026-08-27 afternoon, 2026-08-28), always the same `_is_captcha_present()` TypeError on `None` page_source, always self-heals on retry within the same script run. **Likely real cause, per user (2026-08-28): closing/minimizing the automated Chrome tab mid-run.** SeleniumBase's UC mode pops up a real visible browser window during each `read_events()` call — if that tab gets closed or loses focus while the script is still working, the driver loses its window handle, which matches the `window_handles[-1]` IndexError seen once and is consistent with the browser-session-death pattern behind the other two crashes. Not a soccerdata bug — a workflow habit to fix: leave the SeleniumBase-launched Chrome window alone (don't close/minimize it) until the script finishes. Never recurred after this habit was adopted — no longer chased further, but left open in case it resurfaces during future WhoScored work (e.g. re-running for a new season).

2. **WhoScored team-attribution bug — see Done below for the fix; flagged here as a pattern to watch for.** The original `derive_*.py` functions grouped only by player name, silently dropping team, for weeks before being caught. Worth remembering this class of bug (a groupby silently losing a real dimension) could recur if new derive functions get added later — no specific open instance right now, just a reminder.

3. **`sd.WhoScored()` launches a live Chrome window even when every request should be cache-covered — root cause not conclusively isolated (2026-09-04).** Reprocessing all 13 seasons' already-cached matches through the original `scrape_all_whoscored_matches.py` (to regenerate JSON with the newly player_id-inclusive derive functions) unexpectedly popped up live SeleniumBase Chrome windows, despite `force_cache=True` and despite every match having succeeded in the original extraction. Two candidate explanations, neither confirmed: (a) `sd.WhoScored()`'s constructor itself may launch a browser session on instantiation regardless of whether any individual request needs one, or (b) `output_fmt="raw"` (used by the six pre-2019 fallback-parser seasons) may cache under a separate namespace from the default format, meaning only matches that originally hit the casting bug had their raw-format response cached — every other match in those seasons would have no raw-format cache entry at all. Not chased to a definitive root cause since a workaround was sufficient (see Done below) — worth revisiting if this resurfaces in a context where the workaround doesn't apply.

4. **`data/whoscored/2012-13/` is stale leftover clutter, not part of the real pipeline — confirmed 2026-09-04, worth deleting.** Contains at least one file (`611804.json`) in a format that doesn't match the current pipeline's output shape at all (a plain list of player-name strings per category, not a list of `{player, team, ...stats}` dicts) — almost certainly a leftover from early pre-fix testing. 2012-13 was already confirmed out of scope entirely (a genuine WhoScored data gap, not one of the 13 real usable seasons — see `v1_roadmap.md`), so this folder is never touched by either production script. It's inert, but a directory-wide scan (rather than one scoped to the 13 real `SEASONS`) will pick it up and produce false leads, as it did during the `whoscored_player_id` debugging below. Not deleted yet — flagged for cleanup.

## Done

- FBref access via `soccerdata` + SeleniumBase UC mode (Cloudflare bypass) — confirmed working, `standard`/`shooting`/`misc`/`playing_time`/`keeper` categories return real data.
- WhoScored access confirmed working for NED-Eredivisie via soccerdata (required a custom `WhoScored` entry in `league_dict.json`, same file as the FBref entry). `read_schedule()` and `read_events()` both tested successfully against real matches.
- **`derive_possession_stats.py` penalty-area mislabeling (2026-08-28)** — script originally computed only one penalty-area zone (x ≤ 17, near the defensive goal line) but labeled it `touches_att_pen_area`. Caught via a goalkeeper sanity check: Stijn van Gassel had by far the most touches in that zone (33), which only makes sense for a defensive box. Fixed by splitting into both `touches_def_pen_area` and `touches_att_pen_area`, computed from opposite ends of the pitch (x≤17 vs x≥83). Re-ran and confirmed: keeper now correctly shows 33 in `touches_def_pen_area`, 0 in `touches_att_pen_area`.
- **Calendar refetch inefficiency, root-caused and fixed, CONFIRMED (2026-08-31).** Root cause: `read_events()` unconditionally calls `self.read_schedule(force_cache)` internally on every call, and `read_schedule()`'s caching logic (`no_cache = current_season and not force_cache`) deliberately skips the local cache for an in-progress season unless `force_cache=True` is passed — found by reading soccerdata's actual source (`whoscored.py`). **Fix confirmed via `tests/whoscored/test_whoscored_instance_reuse.py`, re-run with `force_cache=True` on both `read_schedule()` and `read_events()`:** `read_schedule` dropped from 137.0s to 0.2s; the three `read_events()` calls dropped from 129.0s/147.9s/228.6s to 0.1-0.2s each — roughly a 1000x speedup, reproduced identically across two consecutive runs. WhoScored season-scale batch scraping (~300+ matches) is now genuinely fast, not the 10-20+ hour job the unfixed version would have been. Tradeoff still applies: `force_cache=True` won't pick up newly-added fixtures/results — fine for historical batch work, do a `force_cache=False` refresh when current-season data needs to be up to date.
- **Historical season coverage fully mapped and resolved (2026-09-01/02).** Confirmed via full-season batch runs, not inference, across all of 2010-11 through 2025-26:
  - **2020-21 through 2025-26: clean via the standard path.** No issues.
  - **2019-20: genuine partial season, not a bug** — suspended 12 March 2020, formally annulled by the KNVB 24 April 2020 due to COVID-19. 197/250 matches succeeded; the 53 "missing" never happened in real life.
  - **2013-14 through 2018-19: real data confirmed, needed a fallback parser.** soccerdata's standard path crashes (`TypeError: cannot safely cast non-equivalent object to int64`) on how these seasons represent `related_event_id`. `pipelines/whoscored/parse_raw_whoscored_events.py`, built from `output_fmt="raw"`, bypasses the broken casting step. **Fully integrated into `scrape_all_whoscored_matches.py` via `get_events_with_fallback()`** (catches specifically that error message, not a blanket catch-all) and confirmed clean across all 6 seasons at full batch scale — 2013-14 and 2014-15 each 0 missing, 2015-16/2016-17/2017-18 each 0 missing, 2018-19 312/313 (1 single-match gap, not systemic).
  - **2010-11 through 2012-13: confirmed genuine data gaps, not fixable — full seasons tested, not inferred from one match.** 2010-11 and 2011-12 failed on every single match with no data found at all. 2012-13: 311/312 missing. WhoScored simply doesn't have this data. This is the real historical boundary.
  - **FINAL RANGE: 2013-14 through 2025-26 (13 full seasons) is real, usable WhoScored data.**
- **WhoScored team-attribution bug, found and fixed (2026-09-02).** User caught that the loaded player-season table had no way to look up which club a player played for — the `derive_*.py` functions grouped only by player name, silently dropping team entirely, for the whole extraction phase. Fixed by adding `team` to every `groupby()` call across all four `derive_*.py` files, which required switching `scrape_all_whoscored_matches.py`'s JSON output from `orient="index"` (dict keyed by player name) to `orient="records"` (list of dicts with explicit `player`/`team` keys, since a JSON object key can't hold a tuple). All 13 seasons' per-match JSON regenerated from soccerdata's already-cached raw events (fast, no re-scraping). Schema and aggregation script (`aggregate_and_load_whoscored_season.py`) updated to key on `(player_name, team, season_id)`. Confirmed working — Ajax's squad per season now correctly queryable.
- **soccerdata already had team correctly captured from the start** — its multi-index is natively `(league, season, team, player)`, no equivalent bug there. Confirmed, no fix needed.
- **All three sources (Transfermarkt, soccerdata, WhoScored) fully extracted, verified, and loaded into Postgres — extraction phase complete (2026-09-02).**
- **WhoScored `whoscored_player_id` backfill — found, fixed, and fully verified clean (2026-09-04).** WhoScored's raw events already carry a native `player_id` (confirmed present in soccerdata's standard `read_events()` DataFrame via direct column-list inspection, and already captured by `parse_raw_whoscored_events.py`'s fallback parser from the start via its `RENAME_MAP`'s `"playerId": "player_id"` entry) that the four `derive_*.py` functions weren't preserving into their output. This is a separate ID namespace from Transfermarkt's `player_id` — useful as a within-source identity signal and a future entity-resolution cross-check, not a cross-source join key.
  - **Fix:** added `player_id` to every `groupby()` call across all nine stat-producing functions in the four `derive_*.py` files (additive change — same grouping logic, one more column carried through, no restructuring needed this time unlike the team-attribution fix). `aggregate_and_load_whoscored_season.py` updated to capture `player_id` once per `(player, team)` key (constant identity attribute, not summed like the stat fields) and thread it into a new `whoscored_player_id INTEGER` column on `eredivisie_whoscored_player_season_stats`.
  - **Validation:** added `check_player_id_consistency()` to `parse_raw_whoscored_events.py` — confirms every `player_id` resolves to exactly one `player` name within a match, with no unresolved IDs. Confirmed clean on a spot-check match (2015-16, `game_id=956891`).
  - **Reload gotcha #1 — `ON CONFLICT DO NOTHING` silently discarded the entire backfill on first attempt.** `aggregate_and_load_whoscored_season.py`'s original `INSERT_SQL` used `ON CONFLICT (player_name, team, season_id) DO NOTHING`, correct for the original insert-only load but wrong here — every row already existed, so every insert conflicted and was silently dropped, leaving `whoscored_player_id` NULL everywhere despite the derive functions being fixed correctly. **Fixed** by switching to `ON CONFLICT ... DO UPDATE SET` across all columns.
  - **Reload gotcha #2 — `cur.rowcount` under-reports with `execute_values`'s internal paging.** `psycopg2.extras.execute_values` batches inserts into pages (default `page_size=100`) and issues a separate `INSERT` per page; `cur.rowcount` only reflects the *last* page executed, not the cumulative total. Console output showing e.g. "22 rows inserted" for a season with 522 real `(player, team)` pairs was a reporting artifact only — the actual DB write was correct, confirmed via direct `SELECT COUNT(*)`. Worth using `len(rows)` directly instead of `cur.rowcount` in future runs of this script.
  - **The Chrome-popup problem (see Open #3) was worked around, not root-caused**, via a purpose-built cache-only script that reads soccerdata's on-disk cache files directly (`~/soccerdata/data/WhoScored/events/{league}_{season_code}/{match_id}.json`, top-level key confirmed to be `"events"` via direct file inspection) with plain file I/O, never instantiating `sd.WhoScored()` at all. Confirmed zero network/Chrome activity across all 13 seasons using this variant. **This cache-only script is a local-only debugging tool, not part of the real pipeline** — it can't do anything useful on a fresh clone with no existing cache. The original network-capable `scrape_all_whoscored_matches.py` (unchanged in behavior, `force_cache=True` + fallback-parser logic intact) was restored as the canonical version in the repo for forks/fresh clones, with a note added pointing to the cache-only variant for this specific local-reprocessing scenario.
  - **Orphaned garbage rows from an older load, unrelated to the `player_id` fix itself.** After the backfill, 3 rows in `eredivisie_whoscored_player_season_stats` had purely numeric `player_name` values (`'298844.0'`, `'0.0'` ×2 — Cambuur/2022, PSV Eindhoven/2024, Telstar/2025). Root cause: leftover rows from an earlier, buggier load (predating a now-fixed pipeline change) — `ON CONFLICT DO UPDATE` can only update a row whose key matches the *current* run's output, and can never delete a row whose key no longer appears in current data at all. A full scan across all 13 real seasons' current JSON confirmed zero numeric-looking `player` values exist in the source data — the bad rows were pure DB leftovers, not a live bug. **Fixed** via a targeted `DELETE FROM eredivisie_whoscored_player_season_stats WHERE player_name ~ '^[0-9.]+$'` (confirmed exactly 3 rows affected, matching the 3 known-bad rows). Re-verified clean via `SELECT ... WHERE whoscored_player_id IS NULL` returning zero rows.
